How it works

A check on the pull request that changes the spec. Nothing else to review.

The gate runs on the spec you already keep in Git and the docs you already host. It replaces a layer of manual review instead of adding one.

1Connect

Add the check to your workflow

Point it at your OpenAPI file and the surfaces you publish. It runs on every pull request that touches the spec.

.github/workflows/doctorine.yml Example
on:
  pull_request:
    paths: ["openapi.yaml"]
jobs:
  gate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: doctorine/release-gate@v0 # example name
        with:
          spec: openapi.yaml
          tasks: .doctorine/tasks.yaml
2Verify

Agents complete real tasks

Coding agents attempt each task three times against a sandbox generated from the spec, using only the surface under test. A task counts when every run agrees.

.doctorine/tasks.yaml Example
# written from your spec's operations
- id: refund-partial
  task: Refund 12.50 EUR of a
        25.00 EUR payment
  surfaces: [docs, cli, mcp, sdk-ts]
  expect:
    request: POST /v1/refunds
    body.amount: 1250
  runs: 3
3Ship

Publish what passed, keep a receipt

Surfaces that passed publish together from one release. Anything that failed is held back, and the receipt records what was checked.

receipt.json Sample
{
  "release": "4.13.0",
  "surfaces": {
    "docs":   "passed",
    "cli":    "passed",
    "mcp":    "passed",
    "python": "held"
  },
  "agentTasks": { "passed": 24, "runs": 3 },
  "rollback": "4.12.0"
}
What the gate checks

One verdict per surface, for every release.

Every vendor says docs and SDKs stay in sync. The gate shows it on the pull request, surface by surface, before anything is published.

Contract tests per surface

Each SDK, the CLI and the MCP server call a sandbox built from the spec, so a renamed field fails the surface that sends it.

Agent task suite

The integration jobs your users actually do, attempted by coding agents with only your docs, CLI, MCP server or SDK.

Change classification

Bug fix or breaking change, with the consumers it affects. When the gate cannot tell, it asks a person one question.

Hold back, not block

A failing Python SDK does not stop the docs. Passed surfaces ship together and the held one waits for its fix.

Receipts

A signed record of the spec, the generator, every check and every verdict, kept with the release it describes.

One-step rollback

Every surface goes back to the previous release together, so the docs never describe an SDK that is not on the registry.

Why static scores are not enough

Most docs portals are readable. Few tell an agent where the API is.

We ran the free Doctorine analyser on 33 public docs portals on 25 September 2026. The gaps sit in agent and API discovery, which is exactly where a task starts.

27 of 33

had no API Catalog, so an agent cannot find the machine-readable spec from the site.

27 of 33

had no MCP Server Card, the file that tells an agent an MCP server exists.

22 of 33

had no Agent Skills index for the tasks agents are asked to do.

40 / 100

average for agent and API discovery across the 16 scored sites, against 91 for delivery.

Source: Doctorine Docs Analyser, doctorine.dev, runs of 25 September 2026. Scores are static checks; they do not measure whether a task succeeds.

Surfaces

When you want them, generate the rest from one contract.

Doctorine can build the docs portal, TypeScript, Python and Go SDKs, a CLI, an MCP server and Agent Skills from one approved OpenAPI spec, each one passing the same gate.

refund.ts Sample
import Acme from "@acme/payments";

const acme = new Acme({ apiKey: process.env.ACME_API_KEY });

// amount is an integer in the currency's minor unit
const refund = await acme.refunds.create({
  payment: "pay_sample_01",
  amount: 1250,
  reason: "requested_by_customer",
});
