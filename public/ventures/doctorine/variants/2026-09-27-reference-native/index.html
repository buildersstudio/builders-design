Get started / Introduction

Prove every API change works for developers and agents before it ships.

Doctorine runs coding agents through real integration tasks with your docs, SDKs, CLI and MCP server, gates each release on the result, and publishes only the surfaces that passed. The reference below is built the way Doctorine publishes one: generated from a sample OpenAPI spec, with its gate result inline.

Get started

Quickstart #

Start with the free report, then run the same tasks on every pull request that changes the spec. Nothing needs to move: the eval reads the docs you host today.

  1. Run the free eval

    Send a docs URL and your OpenAPI spec. Agents attempt five integration tasks against a sandbox generated from the spec, three runs each.

  2. Apply the fixes

    Each failed task comes with its cause. When the cause is the spec, Doctorine opens one pull request with the mechanical fixes.

  3. Add the gate to CI

    The tasks become a check. Passed surfaces publish together, the rest are held back, and a receipt records the release.

The action, CLI and file names on this page are examples. The gate is being built with design partners.
Example
# .github/workflows/doctorine.yml
on:
  pull_request:
    paths: ["openapi.yaml"]
jobs:
  gate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: doctorine/release-gate@v0 # example
        with:
          spec: openapi.yaml
          tasks: .doctorine/tasks.yaml
          surfaces: docs, cli, mcp, sdk-ts, sdk-python
# .doctorine/tasks.yaml
- id: refund-partial
  task: Refund 12.50 EUR of a 25.00 EUR payment
  expect:
    request: POST /v1/refunds
    body.amount: 1250
  runs: 3
- id: payouts-last-month
  task: List every payout from last month
  expect:
    pagination: exhausted
$ npx doctorine eval --spec openapi.yaml \
    --docs https://docs.acme-payments.example

Release gate

How the gate works #

The gate is a check on the pull request that changes the spec. It rebuilds every surface, runs contract tests and the agent task suite, classifies the change, and writes a receipt.

CheckWhat it decides
contractEach SDK, the CLI and the MCP server call a sandbox built from the spec. A mismatch fails only that surface.
agent-tasksThe task suite from your report, three runs per task, on every surface you publish.
classifyBug fix or breaking change, with the consumers affected. When it cannot tell, it asks one question.
publishPassed surfaces ship together. Failed ones are held back, not the whole release.
receiptA record of the spec, the generator, every check and verdict, with one-step rollback of all surfaces.
For the example release: 38 wording checks, 211 of 212 contract tests and 24 agent tasks passed. A reviewer sees two decisions, not the whole diff.

Spec repair

Repair pull requests #

Point Doctorine at a repository and it checks the spec against what docs, SDKs, the CLI, MCP tools and agents need. Mechanical fixes go into one pull request; anything that changes what your API means is left as a review comment.
