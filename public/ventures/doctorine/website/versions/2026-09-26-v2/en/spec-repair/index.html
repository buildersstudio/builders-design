How it works

From a spec nobody trusts to one reviewable pull request.

  1. 01ScanDoctorine reads openapi.yaml, or the spec behind your public docs, and checks it against what docs, SDKs, the CLI, MCP tools and agents need.
  2. 02ExplainEach problem is described in plain terms, with the operations it affects and the surfaces it breaks.
  3. 03Open one pull requestMechanical fixes land in a single pull request you review like any other. Judgement calls become review comments on the lines they concern.
  4. 04Keep it fixedOnce merged, the release gate checks every later change, so the same problems do not come back.
FAQ

Questions

What does spec repair change on its own?

Only mechanical fixes that do not change what your API means, such as a missing security scheme, a discriminator, consistent naming, examples and documented error responses. Everything else stays a review comment.

Does it merge anything?

No. It opens one pull request and your team reviews and merges it. Branch protection and required checks stay in force.

What if our spec is far from complete?

That is where spec repair is most useful. The report shows how far the spec is from what generation and agents need, and which fixes close most of the gap first.

Is it available now?
