Release gate: publish only the API surfaces that passed

A check on the pull request that changes your spec. It rebuilds every surface, runs contract tests and your agent tasks, holds back anything that failed and writes a receipt of what shipped.

On every spec pull request

Red, then green. Then everything ships together.

  • One verdict per surface: docs, CLI, MCP server, each SDK and the skill.
  • A failed surface is held back with the cause and the one-line fix.
  • Only the affected surface re-runs after the fix.
  • Publishing moves every passed surface to the new release at once.

What the check does

One pull request. Every surface proven.

The gate runs where your spec lives. Times below are from the sample run.

  1. 01
    Read the changeDiff the spec, classify what moved and which surfaces it touches.
    2s
  2. 02
    Build every surfaceDocs, CLI, MCP server, TypeScript, Python and Go SDKs and the Agent Skill, from the same revision.
    1m
  3. 03
    Run contract testsGenerated tests against a sandbox that answers from your spec. No production credentials.
    41s
  4. 04
    Run agent tasksCoding agents try your real integration jobs on each surface, three times. A task counts only when all runs agree.
    2m
  5. 05
    Ask a person only what it could not decideIs a rounding change a fix or a breaking change? That is yours. Everything mechanical is not.
    you
  6. 06
    Publish what passed, togetherEvery passed surface points at the new release at once, and a receipt records why.
    6s

Review

Review two things, not two hundred.

Writing a change takes an agent seconds. Approval is where the weeks go. The gate takes the mechanical review off the list and leaves you only the calls that need a person.

Change classification

Partial refunds now round half-up to the minor unit.

Clients that reconcile totals may see one cent differences. The gate cannot tell whether this is a bug fix or a breaking change for your users.

Terminology rule

The new enum description says delivery reason.

Your style rule says dispatch, never delivery, for fulfilment. It might be deliberate. That is a call for a person, so the gate asks one.

What you can skip: 38 wording checks, 212 contract tests and 24 agent tasks passed on this sample change. The gate reviewed them.

Receipts

Every release leaves a receipt.

The spec hash, the generator and kernel versions and the hash of every output, plus the decisions a person made. Releases are content-addressed and activated through a pointer, so a rollback moves every surface back together.

FAQ

Questions

Where does the release gate run?

As a check on the pull request that changes your spec, in your own repository. Doctorine rebuilds every surface from that revision and reports one verdict per surface next to your other checks.

What happens when one surface fails?

That surface is held back with the reason and the fix. Every surface that passed can still ship together, pointing at the same release.

Does it replace our reviewers?

It replaces the mechanical part of review. Reviewers still decide what a check cannot, such as whether a behaviour change is a fix or a breaking change, and the decision is recorded in the receipt.

What is in a receipt?

The spec hash, the generator and kernel versions, the hash of every output and the decisions a person made. A public example is at doctorine.xyz/proof/doctorine-sdk-receipt.json.

Can we roll back?

Yes. Releases are content-addressed artifacts activated through a pointer, so rolling back moves every surface back to the previous release together.
